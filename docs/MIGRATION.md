# 数据迁移工具使用手册（MIGRATION.md）

> 将手工记账导出的 `house_info.csv` 迁移进维修资金系统，自动补齐小区/楼栋/房屋/业主档案，
> 建立资金账户，按摘要生成缴存单与资金流水，并校验金额勾稽。

## 1. 功能概述

| 能力 | 说明 |
| --- | --- |
| 一键迁移 | 上传 CSV → 预览 → 执行，全程前端操作，自动落库 |
| 档案自动补齐 | 小区、楼栋、房屋、业主不存在时自动创建 |
| 一房多主 | 同一房屋多行不同证件号 → 分别绑定为产权人/共有人 |
| 摘要识别 | 开户 / 缴存 / 分红 / 支用 / 退款 自动映射为对应业务 |
| 金额勾稽 | 缴存、分红记为收入；支用、退款记为支出；余额自动核算 |
| 幂等保护 | 发票号重复的流水自动跳过，防止重复导入 |
| 容错 | 单行失败不影响其它行，执行后输出失败行明细 |
| 编码兼容 | 支持 UTF-8（带/不带 BOM）、GBK、GB18030 |

## 2. CSV 格式与字段说明

模板文件：`migration/house_info_template.csv`（UTF-8 带 BOM）。

| 列名 | 是否必填 | 说明 |
| --- | --- | --- |
| 小区名称 | 是 | 自动建小区（同名复用） |
| 楼 | 是 | 楼栋编号，自动建楼栋（同小区+楼号复用） |
| 单元 | 否 | 为空时房号直接用「房屋」列 |
| 房屋 | 是 | 与「单元」拼接为房号，如单元=3、房屋=302 → 房号 `3-302` |
| 业主姓名 | 是 | 新业主按「证件号码」唯一创建 |
| 证件号码 | 是 | 业主唯一键；同一房屋多行不同证件号 = 一房多主 |
| 证件类型 | 否 | 仅作保留列，不落库 |
| 电梯标志 | 否 | 仅作保留列，不落库 |
| 摘要 | 是 | 识别规则见下表 |
| 交易时间 | 是 | 支持 `yyyy-MM-dd HH:mm:ss`、`yyyy-MM-dd`、`yyyy/M/d`、`yyyy年M月d日` 等 |
| 交易金额 | 是 | 支持 `10,000`、`￥10000`、`10000 元` 等写法；`开户`行可为 0 |
| 发票号 | 否 | 已存在的「发票号+账户」自动跳过 |
| 面积 | 否 | 新房屋建筑面积（㎡），缺省为 0，仅用于展示与缴存数量 |

### 摘要识别规则

| 摘要包含 | 识别类型 | 处理 |
| --- | --- | --- |
| 开户 | OPEN | 仅建立资金账户，金额与流水不变化 |
| 缴存 | DEPOSIT | 余额增加；生成缴存单（状态=已缴 PAID）+ 收入流水（IN） |
| 分红 | DIVIDEND | 余额增加（记入累计缴存）；收入流水（IN） |
| 支用 / 支取 / 使用 | USE | 余额扣减；支出流水（OUT），记入累计使用 |
| 退款 | REFUND | 余额扣减；支出流水（OUT），记入累计退款 |
| 其它 | — | 该行标记为失败，输出错误信息 |

## 3. 使用步骤

### 3.1 准备 CSV

用模板（`migration/house_info_template.csv`）填数，另存为 CSV（建议 UTF-8 带 BOM）。

### 3.2 前端操作

1. 登录（admin 或 property 账号）。
2. 左侧菜单 → **数据迁移** → 点击 **下载模板** 获取空表模板（或使用仓库内 `migration/house_info_template.csv`）。
3. 拖入/选择 CSV → 点击 **预览**，确认列名与示例行无误。
4. 点击 **执行迁移**，二次确认后系统落库。
5. 查看迁移报告：总行数 / 成功行 / 跳过 / 失败行，及新增档案数量。

### 3.3 校验结果

- 综合查询 → 账户查询：逐户核对 `余额 = 累计缴存 - 累计使用 - 累计退款`。
- 综合查询 → 流水查询：每笔缴存/分红为 IN，每笔支用/退款为 OUT，余额为变动后余额。
- 综合查询 → 统计报表：小区汇总与明细一致，末尾「合计」行等于各小区之和。

### 3.4 接口方式（可选）

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"admin","password":"admin123"}' \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")

# 预览
curl -s -X POST http://localhost:8080/api/migrate/preview \
  -H "Authorization: Bearer $TOKEN" -F "file=@migration/house_info.csv"

# 执行
curl -s -X POST http://localhost:8080/api/migrate/execute \
  -H "Authorization: Bearer $TOKEN" -F "file=@migration/house_info.csv"
```

权限：`POST /api/migrate/preview`、`POST /api/migrate/execute` 仅 `ADMIN` / `PROPERTY` 可用。

## 4. 迁移报告字段

| 字段 | 含义 |
| --- | --- |
| totalRows | 文件总数据行数 |
| communityCreated / buildingCreated / houseCreated / ownerCreated / accountCreated | 本次新增的档案数（已存在则复用不计数） |
| depositCreated | 生成的缴存单数（缴存行） |
| flowCreated | 生成的资金流水数（缴存/分红/支用/退款行） |
| skipped | 因发票号重复被跳过的行数 |
| errorRows / errors | 失败行数与明细（第 N 行 + 原因） |

## 5. 业务规则与注意点

1. **金额勾稽**：`balance = totalDeposit - totalUsed - totalRefund` 由系统自动核算；分红计入累计缴存。
2. **一房多主**：同一房屋首行证件号为产权人（主），后续不同证件号自动绑定为共有人。
3. **幂等**：发票号 + 账户 已存在流水则跳过该行；建议迁移后不要再重复导入同一文件。
4. **开户行金额**：`开户` 行金额可填 0（仅开户不产生流水）；也可在同文件后续 `缴存` 行体现首次缴存。
5. **失败行**：未知摘要、时间格式错误、金额非法、缺少必填列等记为失败行；修正后可重新导入整个文件（已成功行因幂等会被跳过）。
6. **演示数据隔离**：演示库自带「阳光花园 / 幸福里小区」演示档案，迁移时建议使用新小区名，避免与演示数据混用。

## 7. 常见问题

| 问题 | 处理 |
| --- | --- |
| 提示「文件缺少列」 | 表头列名与模板不一致，请使用模板列名 |
| 提示「CSV 解析失败」 | 文件不是标准 CSV（分隔符不是逗号）；检查是否以逗号分隔 |
| 行报「无法识别的摘要」 | 摘要未包含开户/缴存/分红/支用/退款，可调整摘要文字或人工处理该行 |
| 行报「交易时间无法解析」 | 日期格式不在支持列表，统一为 `yyyy-MM-dd` |
| 重复导入会不会重复入账 | 不会，发票号重复自动跳过 |

## 8. 表结构变更与迁移工具维护

迁移工具**没有独立的数据库/表结构**，它直接复用系统的 JPA 实体与 Repository
（`Community/Building/House/Owner/HouseOwner/FundAccount/Deposit/FundFlow`），与系统业务写入同一套表，
因此不存在"迁移库"与"实际库"结构漂移的问题。

### 8.1 表结构变更时的维护要点

| 变更类型 | 处理方式 |
| --- | --- |
| 新增普通列 | H2 开发库 `ddl-auto: update` 重启自动加列；MySQL 生产库在 `sql/schema.sql` 追加 `ALTER TABLE`，不改动已执行脚本 |
| 新增必填列 | 在实体给默认值，或同步在 `MigrationService` 导入时补值（如 `area/status/openTime` 已如此处理） |
| 字段改名 / 删除 | 同版本内同步修改实体 + 迁移代码，编译期即可发现遗漏 |
| 新增唯一约束 | 幂等由发票号 + 账户 兜底，重复导入自动跳过，不产生重复流水 |
| 拆分 / 合并表 | 同步改造迁移落库逻辑，迁移前在测试库验证统计勾稽 |

### 8.2 变更后上线建议

1. 在临时/测试库执行 `migration/house_info.csv`，核对：
   `余额 = 累计缴存 - 累计使用 - 累计退款`，统计合计与明细一致。
2. 全量回归 `docs/TESTING.md` 中 2.8 迁移用例（MIG-01~08）。
3. 确认无误后再对生产库执行迁移。
4. 迁移完成后业务查询与手工台账抽样比对（余额、流水笔数、发票号）。
